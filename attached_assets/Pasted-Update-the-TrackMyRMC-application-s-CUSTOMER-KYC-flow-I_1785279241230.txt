2. Secondary button:
   “Back to Home”

6. Do not collect the Aadhaar OTP inside TrackMyRMC.
7. Do not hard-code DigiLocker URLs, client IDs, client secrets or redirect URLs in frontend code.
8. Protect the authorization request using the existing secure state or PKCE implementation.
9. Disable the button while the authorization request is being created to prevent duplicate requests.

Button loading text:

7. DIGILOCKER CALLBACK AND STATUS UPDATE
==================================================

Inspect and reuse the project’s existing DigiLocker callback implementation.

After successful DigiLocker authorization:

1. Validate the state/PKCE value on the backend.
2. Exchange the authorization code on the backend only.
3. Fetch the permitted verified identity information using the existing integration.
4. Match the result with the currently authenticated TrackMyRMC customer.
5. Update the customer KYC record.
6. Store only the minimum data required by the application.
7. Never store DigiLocker OTPs.
8. Never log access tokens, refresh tokens, Aadhaar numbers or sensitive identity payloads.
9. Record the verification provider as “digilocker”.
10. Record the verification timestamp.
11. Record the provider reference ID where permitted.
12. Return or deep-link the customer back to the TrackMyRMC KYC screen.
13. Automatically refresh the KYC status after returning to the app.

Use an application deep link similar to the existing TrackMyRMC deep-link configuration. Do not invent a new scheme if one already exists.

9. ONLY VERIFIED CUSTOMERS CAN PLACE ORDERS
==================================================

A customer whose KYC is not verified must not be allowed to place an order.

Implement this rule in both frontend and backend.

Frontend:

- When a non-verified customer clicks “New Order” or the centre “NEW” button, check KYC status.
- If verified, open the order screen.
- If not verified, redirect to the KYC screen.
- Show the message:

  “Complete KYC to Place an Order”

  “DigiLocker verification is required before you can place a concrete order.”

- Provide a “Complete KYC” button.

Backend:

- Protect every customer order-creation endpoint.
- Load the authenticated customer from the database.
- Confirm that `kycStatus === "verified"` and `isKycVerified === true`.
- Do not trust a value submitted by the frontend.
- Return HTTP 403 for a non-verified customer.

Use a consistent response similar to:

{
  "success": false,
  "code": "KYC_REQUIRED",
  "message": "Complete DigiLocker KYC before placing an order."
}

Do not block customers from:

- Viewing previous orders
- Viewing plants
- Viewing their profile
- Accessing help and support
- Completing KYC

Only order creation and other legally restricted customer actions should be blocked.

11. AUTHENTICATION AND SECURITY
==================================================

- Every KYC route must require authentication.
- A customer may only read or update their own KYC status.
- KYC provider secrets must remain in server environment variables.
- Never expose client secrets in Vite, React or Capacitor bundles.
- Validate callback state and prevent CSRF.
- Prevent duplicate callback processing.
- Make callback processing idempotent.
- Sanitize logs.
- Do not log complete provider responses.
- Mask sensitive identifiers in admin views.
- Use HTTPS redirect and callback URLs.
- Maintain an audit record of status changes without storing unnecessary identity data.
- Do not accept `verified: true` from a frontend request.
- Verification must only be set after a valid server-side DigiLocker callback or approved server-side reconciliation.
