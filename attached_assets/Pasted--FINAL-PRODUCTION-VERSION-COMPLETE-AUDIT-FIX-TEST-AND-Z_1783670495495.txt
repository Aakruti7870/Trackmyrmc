## FINAL PRODUCTION VERSION — COMPLETE AUDIT, FIX, TEST AND ZIP

Please create the **final production-ready version** of the application.

Do not immediately generate the ZIP file. First, fully inspect, correct, test and confirm every requirement below.

### 1. Mobile and Display-Fit Audit

Review the complete application and confirm that every screen fits correctly on:

* Android mobile phones
* Small mobile screens
* Large mobile screens
* Tablets
* Desktop and laptop displays
* Different screen resolutions and aspect ratios
* Portrait and landscape orientation where supported

Use a consistent responsive layout system throughout the application.

Requirements:

* No horizontal scrolling.
* No unwanted page scrolling on the Landing Page and Login Page.
* No text, buttons, cards, menus or widgets should overflow outside the screen.
* No clipped headings, collapsed footer text or overlapping components.
* No excessive empty space.
* No fixed-width layout that breaks on smaller displays.
* Use responsive sizing such as `width: 100%`, `max-width`, flexible grids, flexbox and media queries where required.
* Properly handle safe areas, mobile browser bars, Android navigation bars and notches.
* Use `min-height: 100dvh` or another reliable mobile viewport solution instead of depending only on `100vh`.
* All buttons must remain fully visible and touch-friendly.
* Font sizes, cards, margins, gaps and padding must scale correctly.
* Header and bottom navigation bars must have the correct width and height.
* Fixed headers and bottom navigation must not cover page content.
* Modal windows, dropdowns, side menus and expandable widgets must remain inside the visible screen.
* Opening one navigation section must not block interaction with another section.
* When another bottom navigation tab is selected, the currently opened More menu must automatically close.

Create a clean and reusable page-frame structure so every screen follows the same layout system:

1. Safe-area wrapper
2. Application header
3. Main scrollable or fixed content section
4. Floating or centre action area where applicable
5. Bottom navigation
6. Modal and overlay layer

Do not apply random page-by-page CSS patches. Correct the shared layout architecture.

### 2. Landing Page and Login Page

The first two screens must fit entirely within the mobile viewport.

#### Landing Page

#### Login Page

* Login card must remain centred and properly sized.

Check and improve:

* Initial loading speed

* Image sizes and formats
* Unnecessary re-renders
* Duplicate API calls
* Memory leaks

* Unused dependencies

Use:

* Lazy loading where appropriate

* Image optimisation
* Request cancellation and timeout handling

* Debouncing and throttling where required
* Pagination or virtualisation for large records
* Proper loading states
* Proper empty states
* Proper error states
* Retry logic only where safe
* Optimistic updates only where reliable

Do not compromise data accuracy for performance.

* Reports

The application must refresh relevant information automatically in the background.

### 5. Background Auto-Refresh

Implement stable background data synchronisation.

Requirements:

* Refresh only the required data, not the entire page.
* Do not visibly reload the application.
* Do not reset the current page, selected tab, open form or scroll position.
* Do not interrupt typing or data entry.
* Do not create duplicate requests.
* Pause or reduce polling when the app is in the background.
* Resume safely when the app becomes active.
* Prevent overlapping API requests.
* Clear intervals and subscriptions when components are unmounted.
* Use real-time listeners, WebSockets or server events where already supported.
* Otherwise use controlled polling with a sensible interval.
* Use immediate refresh after important actions such as order creation, trip assignment, status changes, dispatch completion and delivery completion.
* Display a subtle last-synced status only where useful.
* When offline, retain unsent actions safely and synchronise after reconnection where supported.
* Never create duplicate orders, challans, status records or messages during reconnection.
