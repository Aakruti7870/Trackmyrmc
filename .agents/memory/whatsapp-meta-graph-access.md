# Meta Graph API access from this app's server

**Asset-graph reads DO work; only identity edges are blocked.** With the System-User token, GET on managed assets works fine from the Replit server: `/{waba_id}/phone_numbers`, `/{business_id}/owned_whatsapp_business_accounts`, `/{waba_id}?fields=account_review_status,business_verification_status`, `/{business_id}?fields=verification_status`. POST also works: send messages, create templates, `/{waba_id}/phone_numbers` (add number). What returns `{"error":"API access blocked.","code":200}` are **identity/permission edges** (`/me`, `/me/permissions`, `debug_token`) — those need user-level perms a system-user token lacks. So: query account state directly, but get token-scope/debug info from the user.

**How to apply:**
- You CAN discover Phone Number ID / WABA list / verification state via Graph from here (asset reads work). Only token *scope*/debug info needs the user (screenshots of *WhatsApp → API Setup*).
- The auto-created WABA named **"Test WhatsApp Business Account"** is a sandbox: it allows only the +1 test number (phone-number limit 1). Adding a real number returns `(#100, subcode 2388112) Phone Numbers Count Exceeded Limit Per Business`. **Adding a payment method does NOT lift this** (verified that empirically). The limit is the sandbox WABA itself; a real number needs a **production WABA created via browser Embedded Signup** (developers.facebook.com → app → WhatsApp → API Setup → "Add phone number", or business.facebook.com/wa/manage). A System-User token scoped to the sandbox WABA CANNOT create a production WABA via API. Business/portfolio being `verified` does not change this.
- Known Meta wizard bug during that browser onboarding: `Unexpected null value for wabaID [WhatsAppBizPlatformPhoneCreationContainer.react]` — cache/state corruption; fix by retrying in a fresh incognito window / different browser / clearing facebook.com cookies, with the correct Business selected.
- **Embedded Signup creates a NEW production WABA that the existing System-User token CANNOT see** (it stays scoped to the original test WABA; `owned_whatsapp_business_accounts` won't list the new one, and reading its id returns subcode-33 missing-permissions). To make the app usable on the new number you MUST either (a) assign that System User to the new WABA in Business Settings → System users → Add assets → WhatsApp accounts → Manage, then the same token works, or (b) generate a fresh token from a user that has the new WABA. The Meta-provided +1 **test number cannot be deleted via API** (subcode 33), so you can't free the sandbox WABA's single slot to reuse it.
- Indian **debit cards** frequently fail Meta's "Add payment method" with "Something went wrong" because Meta bills recurring-international; even with International toggled on, debit often can't authorize recurring mandates — credit card (incl. app-based: Slice/Uni/Fi/Jupiter/Kiwi) is the reliable route.
- You **can** create message templates and send messages programmatically via curl using `$WHATSAPP_META_ACCESS_TOKEN` (the secret IS visible to the bash shell here, unlike some shared env vars).
- Free **test** numbers only deliver to numbers added to the API Setup **recipient allow-list** (else `(#131030) Recipient phone number not in allowed list`). Reaching real customers needs Production setup (own business number + payment + display-name review) — a user-only step.
- A wrong/foreign Phone Number ID yields `(#100/subcode 33) object does not exist or no permission` on send — symptom of an ID that the token's WABA doesn't own.
- **Cloud API number activation sequence** once a real number sits on an accessible WABA: (1) `POST /{phone_number_id}/request_code?code_method=SMS&language=en_US` → SMS OTP to the number; (2) `POST /{phone_number_id}/verify_code?code=NNNNNN` → flips `code_verification_status` to VERIFIED; (3) `POST /{phone_number_id}/register` with JSON `{"messaging_product":"whatsapp","pin":"NNNNNN"}` (the 6-digit two-step PIN you choose). Only after register does `status` go PENDING→CONNECTED and the number can send.
- **`/register` blocker — "Phone Link to WABA Failed - Unverified WABA"** (`(#100) Invalid parameter`): a freshly-created production WABA has `account_review_status: PENDING` and register is blocked until it becomes APPROVED. Note `business_verification_status:"verified"` and `on_behalf_of_business_info.status:"APPROVED"` are SEPARATE and NOT sufficient — the WABA's own account review must pass (automatic, minutes→~24h). Don't switch `WHATSAPP_META_PHONE_NUMBER_ID` to the new number until register succeeds, or the app's sends start failing; keep the working test number until then.

## App-level webhook subscription via API (works despite blocked reads)
- App ID for CONCRETE KING Meta app: 1741942050318808. The WHATSAPP_META_ACCESS_TOKEN is a SYSTEM_USER token, never-expiring, scopes: business_management + whatsapp_business_management + whatsapp_business_messaging.
- You CAN set the webhook entirely by API even though object reads (phone/WABA) return 400 "missing permissions": `POST /v21.0/{app-id}/subscriptions` with app access token `{app_id}|{app_secret}`, body object=whatsapp_business_account, callback_url, verify_token, fields=messages,... → {"success":true}. Confirm with `GET /{app-id}/subscriptions` (active:true).
- What's NOT confirmable by API here: the WABA→app `subscribed_apps` link and the WABA ID itself (reads blocked; candidate WABA ids 1638401933904127/1336143745078768 both 400). If inbound doesn't arrive after app-level sub, get the WABA ID from the user's API-Setup screen and `POST /{waba-id}/subscribed_apps`.
