# CONCRETE KING — Android App (Capacitor)

This wraps the existing React web app (`rmc-app/`) in a native Android shell using
[Capacitor](https://capacitorjs.com/). The same frontend code runs inside a WebView
and talks to the **deployed** backend over the internet.

- **App ID:** `com.trackmyrmc.concreteking`
- **App name:** CONCRETE KING
- **Native project:** `rmc-app/android/` (open this in Android Studio)

---

## 1. Point the app at your deployed backend

The native app is not served same-origin and has no dev proxy, so it must call the
live backend with an absolute URL. This is configured in **`rmc-app/.env.capacitor`**:

```
VITE_API_BASE_URL=https://www.trackmyrmc.com   # your deployed backend, no trailing slash
VITE_DISABLE_PWA=1                             # disable the PWA service worker in the native bundle
```

Change `VITE_API_BASE_URL` if your live domain differs. This value is baked into the
JS bundle at build time. The web build (`pnpm build`) ignores this file, so the
browser/PWA version keeps using relative `/api` and a service worker as before.

> The deployed backend's CORS allowlist already permits the native origin
> (`https://localhost` / `capacitor://localhost`) and the goldetech web domains.
> If you serve the backend from a different host, add it to the `CORS_ALLOWED_ORIGINS`
> environment variable on the server (comma-separated).

---

## 2. Build the web assets and sync them into Android

From `rmc-app/`:

```bash
pnpm cap:sync
```

This runs `pnpm build:native` (a production Vite build in `capacitor` mode — no service
worker, API pointed at the deployed backend) and then `cap sync android`, which copies
`dist/` into the native project and updates native dependencies.

Run this every time you change the frontend or the backend URL.

### Refreshing icons & splash (only when branding changes)

The launcher icon and splash screen are generated from `rmc-app/assets/logo.png`
(gold crown on transparent) into the navy theme:

```bash
pnpm cap:assets
```

---

## 3. Open and run in Android Studio

```bash
npx cap open android      # from rmc-app/, or open rmc-app/android/ manually
```

In Android Studio, let Gradle sync, then **Run** on an emulator or a connected device
to smoke-test. The app should load the deployed CONCRETE KING site inside the WebView,
on a navy splash with the gold crown icon.

---

## 4. Create a signing keystore (one time)

A `.aab` for the Play Store must be signed. Create a keystore once and keep it safe —
**if you lose it you cannot update the app on the Play Store.**

```bash
keytool -genkey -v \
  -keystore concreteking-release.keystore \
  -alias concreteking \
  -keyalg RSA -keysize 2048 -validity 10000
```

You will be prompted for a keystore password, a key password, and your org details.
Store the keystore file and both passwords somewhere secure (a password manager). Do
**not** commit the keystore — `android/.gitignore` already excludes `*.keystore` /
`*.jks` and `*.aab`.

---

## 5. Build a signed `.aab`

### Option A — Android Studio (recommended)

1. **Build → Generate Signed App Bundle / APK…**
2. Choose **Android App Bundle**, click **Next**.
3. Select your `concreteking-release.keystore`, enter the keystore password, pick the
   `concreteking` key alias, and enter the key password. Click **Next**.
4. Choose the **release** build variant, click **Create**.
5. The signed bundle is written to:
   `rmc-app/android/app/release/app-release.aab`

### Option B — Gradle CLI

Add the signing config to `android/app/build.gradle` (or supply it via
`-P` properties / `~/.gradle/gradle.properties`), then from `rmc-app/android/`:

```bash
./gradlew bundleRelease
# → app/build/outputs/bundle/release/app-release.aab
```

Upload the resulting `.aab` to the Google Play Console.

---

## 6. Bumping the version for each release

Edit `android/app/build.gradle`:

```gradle
android {
  defaultConfig {
    versionCode 3          // integer, must increase every Play upload
    versionName "1.2"      // human-readable
  }
}
```

---

## Notes

- **Push notifications:** web-push (VAPID / service worker) does not run inside the
  native WebView; the app degrades to a no-op there. In-app SSE notifications still
  work because the WebView reaches the deployed backend directly.
- **Photos / files** (proof, bills, object storage) are already served as absolute
  signed URLs, so they work unchanged in the native app.
- `android/app/src/main/assets/public/` (the copied web bundle) is git-ignored and
  regenerated by `pnpm cap:sync`; never edit it by hand.
